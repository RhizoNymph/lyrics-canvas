# Helm Deployment

A Helm chart under `deploy/helm/lyrics-canvas` that runs the web stack on
Kubernetes, plus the production frontend image it needs
(`frontend/Dockerfile.prod`). Docker Compose remains the development setup
(see [INFRASTRUCTURE.md](../INFRASTRUCTURE.md)).

## Scope

- Kubernetes manifests for the backend API, the frontend, and an optional
  bundled PostgreSQL + pgvector, generated by one chart.
- Alembic migrations run automatically before the API starts.
- Secrets (JWT signing key, database password) generated on first install and
  preserved across upgrades, or supplied from existing Secrets.
- An optional Ingress with same-host path routing and TLS.
- A production frontend image: Vite build served by nginx, `/api` reverse
  proxied to the backend Service.
- A render-and-assert test suite for the chart.
- Committed per-cluster values files (`deploy/helm/environments/`) with
  credentials kept out of git.

## Non-scope

- Building or publishing the container images (no CI pipeline is included).
- High availability for PostgreSQL, backups, or connection pooling.
- Autoscaling, network policies, pod disruption budgets.
- The Android client (it only needs the API URL).

## Control flow

### Install

1. `helm install` validates the merged values against `values.schema.json`
   (unknown keys and wrong types fail before anything is created).
2. Secrets render first in template order but are independent of each other.
   `lyrics-canvas.backend.secretKey` and `lyrics-canvas.postgres.password`
   (in `_helpers.tpl`) use an explicit value when given, otherwise `lookup`
   the live Secret and reuse its value, otherwise `randAlphaNum`. Under
   `helm template` there is no cluster, so a fresh random value appears each
   render.
3. The PostgreSQL StatefulSet starts with the chart's initdb ConfigMap mounted
   at `/docker-entrypoint-initdb.d`; on an empty data directory the image runs
   `CREATE EXTENSION IF NOT EXISTS vector`. `PGDATA` points at a subdirectory
   so a provisioned volume's `lost+found` does not block initdb.
4. Each backend pod runs the `migrate` init container (same image as the API)
   which loops `uv run alembic upgrade head` until it succeeds or
   `backend.migrations.attempts` is exhausted, sleeping
   `backend.migrations.delaySeconds` between tries. This both waits for the
   database and applies migrations. Concurrent replicas may collide on DDL;
   the loser's init container fails, Kubernetes restarts it, and the retry
   is a no-op at head.
5. The API container starts. `app.main` still runs `Base.metadata.create_all`
   at startup, which is a no-op once Alembic has created the tables, so the
   `alembic_version` table is correctly stamped from the first boot.
6. The frontend container renders `/etc/nginx/templates/default.conf.template`
   through the image's envsubst entrypoint, substituting `BACKEND_URL`
   (`http://<release>-backend:<port>`).
7. The `helm test` pod fetches `/healthz` on the frontend Service and
   `/api/health` on the backend Service.

### Request flow

```
browser -> Ingress host
             /api/*  -> backend Service :8000 (ingress.routeApiToBackend=true)
             /*      -> frontend Service :80 -> nginx :8080
                                                 /api/*   proxy_pass $BACKEND_URL
                                                 /assets/ immutable cache
                                                 /*       try_files ... /index.html (SPA)
```

Because the SPA is built with `VITE_API_URL=""`, it always calls `/api`
relative to its own origin. That is why no CORS configuration is needed for
the single-host setup; `CORS_ORIGINS` is still populated from the ingress
hosts so a frontend served elsewhere can be allowed explicitly via
`backend.corsOrigins`.

### Database URL wiring

With the bundled PostgreSQL, the backend's `DATABASE_URL` is a literal
`postgresql+asyncpg://<user>:$(POSTGRES_PASSWORD)@<release>-postgres:5432/<db>`
and `POSTGRES_PASSWORD` is a `secretKeyRef` listed before it. Kubernetes
expands `$(VAR)` at container start, so the password never appears in the
Deployment manifest and the same Secret feeds both the database and the API
(including an operator-provided `postgres.auth.existingSecret`).

With `postgres.enabled=false`, `DATABASE_URL` comes from a `secretKeyRef`:
either the chart's backend Secret (`database-url`, filled from
`externalDatabase.url`) or `externalDatabase.existingSecret`. Rendering fails
with a clear message when neither is set.

| `deploy/helm/lyrics-canvas/values.yaml` | All tunables with comments. |
| `deploy/helm/lyrics-canvas/values.schema.json` | JSON Schema; `additionalProperties: false` on every section, enums for pull policy / service type / access modes, quantity pattern for sizes. |
| `deploy/helm/lyrics-canvas/templates/_helpers.tpl` | Names, labels, image refs, secret lookups, `databaseEnv`, `corsOrigins`, service URLs. |
| `templates/backend/deployment.yaml` | API Deployment with `migrate` init container, probes on `/api/health`, `HF_HOME=/cache` volume (emptyDir or PVC). |
| `templates/backend/secret.yaml` | `secret-key` and, for an external database URL, `database-url`. Skipped entirely when both come from existing Secrets. |
| `templates/backend/pvc.yaml` | Optional model cache claim. |
| `templates/backend/service.yaml` | ClusterIP (configurable) on `backend.service.port`. |
| `templates/frontend/deployment.yaml` | nginx Deployment; `BACKEND_URL` env; probes on `/healthz`. |
| `templates/frontend/service.yaml` | Service on `frontend.service.port` to container port 8080; `nodePort` is set only for `type: NodePort` with `frontend.service.nodePort`. |
| `templates/postgres/statefulset.yaml` | Single replica pgvector with `volumeClaimTemplates` (or emptyDir). |
| `templates/postgres/secret.yaml`, `service.yaml`, `configmap-initdb.yaml` | Password, ClusterIP, `01-init.sql`. |
| `templates/ingress.yaml` | One rule per host: optional `/api` to backend, `/` to frontend; TLS passthrough from values. |
| `templates/serviceaccount.yaml` | Shared service account with token automount off. |
| `templates/tests/test-connection.yaml` | `helm test` hook. |
| `templates/NOTES.txt` | Post-install access instructions. |
| `deploy/helm/lyrics-canvas/README.md` | Image build, install and configuration guide. |
| `deploy/helm/tests/test_chart.py` | `unittest` suite: `helm lint --strict` plus renders of the fixtures in `deploy/helm/tests/values/` with structural assertions. |
| `deploy/helm/environments/homelab.yaml` | Values for the home microk8s cluster (registry `localhost:32000`, node0/node1 affinity, NodePort 32443). Rendering it matches the live `lyrics` release. |
| `.gitignore` (`deploy/helm/environments/*.secret.yaml`) | Keeps per-environment credential overrides out of git. |
| `frontend/Dockerfile.prod` | Multi-stage: `node:20-slim` build (`npm ci`, `npm run build`) into `nginxinc/nginx-unprivileged:1.27-alpine`. Build args `VITE_API_URL`, `VITE_GOOGLE_CLIENT_ID`. |
| `frontend/nginx/default.conf.template` | Server block on 8080: `/healthz`, `/api/` proxy, SPA fallback, asset caching. |
| `frontend/.dockerignore` | Keeps `node_modules` and `dist` out of both image builds. |

## Invariants and constraints

- Every workload uses the same selector labels
  (`app.kubernetes.io/name`, `instance`, `component`); Services select on
  exactly those. Changing them is a breaking change for existing releases
  (Deployment selectors are immutable).
- A generated secret must never change on `helm upgrade`: the helpers always
  consult `lookup` before generating. Rotating is deliberate: set
  `backend.secretKey` / `postgres.auth.password` or delete the Secret.
- `postgres.auth.password` is placed verbatim in a URL; it must not contain
  characters that need percent-encoding. Generated passwords are alphanumeric.
- `backend.image.tag` and `frontend.image.tag` fall back to `Chart.appVersion`;
  the PostgreSQL tag falls back to `pg16`.
- The `/api` ingress path and the nginx `/api/` proxy both resolve to the same
  backend Service, so either path is correct; the ingress route only skips a
  hop.
- `backend.modelCache.persistence.accessModes` must be `ReadWriteMany` if
  `backend.replicaCount > 1` and pods can land on different nodes; the chart
  does not enforce this.
- Pods must start without internet access. Both the backend image and the
  chart (on the `migrate` init container and the API container) set
  `UV_NO_SYNC=1`, so `uv run` uses the venv built into the image and never
  re-resolves or rebuilds the project (which would fetch `hatchling` from
  PyPI on every pod restart). The chart sets it too so older images are safe.
- Committed values files (the chart's `values.yaml` and
  `deploy/helm/environments/*.yaml`) leave `backend.secretKey`,
  `postgres.auth.password` and `externalDatabase.url` empty;
  `CommittedValuesSafetyTest` enforces this and checks that
  `*.secret.yaml` overrides are gitignored. A new credential-bearing value
  must be added to `SECRET_PATHS` in the test suite.
- The chart test suite must pass (`python3 deploy/helm/tests/test_chart.py`)
  and rendered output must validate with `kubeconform -strict`.
